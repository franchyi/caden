Design Document

Branching KV Cache for Agent Chat Sessions

Tree-structured session management with copy-on-write KV forking, tool-sandbox branches, and cold-storage persistence — built natively on SGLang RadixAttention, with optional kvcached VMM for GPU memory elasticity.

Draft v0.2 2026-07-07 Status: RFC
Section 1

Problem Statement

Agent chat sessions are not linear. Users edit earlier messages, regenerate responses, backtrack from dead-end trajectories, and explore alternative tool calls. Agents themselves need to speculatively execute tools in sandboxes and roll back on failure. Today's LLM serving engines treat conversations as flat token sequences — there is no concept of "branch here", "switch to branch B", or "undo the last tool call."

SGLang's RadixAttention already contains the core primitives — prefix sharing via a radix tree, reference counting, node splitting at divergence — but exposes none of them as session-level operations. This document designs the system that bridges session semantics and cache mechanics, built as native SGLang modifications.

Section 3

Architecture: SGLang-Native with Optional Plugins

All branching features are built as native SGLang modifications. Cold storage and GPU memory elasticity are optional plugins for deployments that need them.

Session
Branch Manager  —  new module in sglang.srt.mem_cache: named branches, fork / switch / pin / delete API, sandbox lifecycle, two-phase commit new
Cache
SGLang RadixAttention  —  radix tree extended with branch metadata, tree-aware eviction, segment-aware matching, attention kernels extended
Cold Store
LMCache / Mooncake  —  tiered KV persistence (CPU DRAM → NVMe → Redis → S3), KV compression, cross-node transfer optional plugin
Memory
SGLang KV Pool (default) or kvcached VMM (optional)  —  block allocation for KV tensors kvcached optional

Why SGLang-native

Every branching feature — branch identity, tree-aware eviction, sandbox lifecycle, segment-aware matching, shared-prefix kernels — is a modification to SGLang internals (radix tree, scheduler, attention backend). No external framework provides these. Building them natively in SGLang gives direct access to the internals that matter, avoids monkey-patching fragility, and produces a single codebase to maintain.

  • Branch Manager is a new module in sglang.srt.mem_cache. It knows about sessions, tool calls, and user intent. It translates "fork here" into radix tree operations and "sandbox this tool" into branch + pin + environment snapshot.
  • RadixCache is extended with branch metadata on nodes, tree-topology-aware eviction, and segment-aware prefix matching. These are surgical modifications to existing code paths.
  • LMCache / Mooncake (optional) catches KV evicted from GPU before it's discarded entirely. LMCache already integrates with SGLang — the cold-store tier connects directly to the eviction path. Without it, eviction means full re-computation on branch revival.
  • kvcached (optional) replaces SGLang's static KV pool with elastic GPU virtual memory. Useful for multi-model GPU sharing and scale-to-zero, but not required for branching — SGLang's existing pool + eviction handles branch workloads adequately.

Three engineering patterns considered

Decision: Pattern C — SGLang-native + optional plugins

Build all branching features as native SGLang modifications. The Branch Manager, tree-aware eviction, sandbox lifecycle, segment-aware matching, and shared-prefix kernel are all modifications to sglang.srt.mem_cache and sglang.srt.managers. They work with SGLang's existing KV pool allocator — no kvcached required.

kvcached is an optional deployment plugin for environments that need GPU memory elasticity (multi-model GPU sharing, scale-to-zero, colocation with training). It integrates via its existing autopatch mechanism and is independent of branching.

LMCache is an optional cold-storage plugin for deployments where branch revival latency matters. It connects to SGLang's eviction path to demote KV before discarding. Without it, evicted branches are re-prefilled from token history.

Why SGLang's existing KV pool is adequate for branching

A concern with the SGLang-native approach is that SGLang pre-allocates a fixed-size KV pool at startup. Won't branching need elastic memory?

No — for the branching use case specifically:

  • Branch creation is already "zero-cost" in vanilla SGLang. When a new sequence shares a prefix, match_prefix() finds the cached prefix — no new KV blocks are allocated for the shared portion. Only newly generated tokens need new blocks.
  • Idle branches consume only their unique suffix. For a typical agent session with 5–20 branches, most idle, the total unique KV across all branches is 2–5× the active branch length. The pre-allocated pool accommodates this easily.
  • Memory pressure is handled by eviction, which we're improving. Tree-aware eviction with descendant weighting ensures shared prefixes survive while dead-end branches are reclaimed. This is exactly what the fixed pool + smart eviction model is designed for.
  • kvcached's VMM value is orthogonal. GPU memory elasticity helps when multiple models share a GPU or when LLM serving colocates with other workloads. These are real deployment concerns but they're independent of branching — you can compose kvcached with branching at deployment time without coupling them at design time.
Section 5

Optional Plugins: kvcached and LMCache

Branching works with SGLang's stock allocator. These plugins are additive — they improve specific deployment scenarios without changing the branching design.

kvcached: when to enable

kvcached replaces SGLang's static KV pool with GPU virtual memory (CUDA VMM). It maps physical pages lazily on demand and unmaps them when freed. Enable it when:

  • Multiple models share a GPU. Agent sessions that switch models benefit from elastic memory sharing — the old model's KV is unmapped, the new model maps into freed physical pages. No static partitioning.
  • LLM serving colocates with other GPU workloads. Training, fine-tuning, or vision models can reclaim GPU memory when the LLM is idle.
  • Scale-to-zero / serverless. Models can release all physical memory when idle and re-acquire it on the next request.

kvcached integrates via its existing autopatch mechanism — it monkey-patches SGLang's TokenToKVPoolAllocator and MHATokenToKVPool at import time. The branching modifications (Branch Manager, eviction policy, radix tree extensions) operate above the allocator interface and are unaffected by whether kvcached is enabled.

Design constraint: branching modifications must not break kvcached's autopatch surface. The allocator interface (alloc(), free(), available_size()) is the clean boundary. Branching extends the radix tree and scheduler; kvcached replaces the allocator. These are non-overlapping concerns.

LMCache: when to enable

LMCache provides tiered KV persistence — CPU DRAM, NVMe, Redis, S3 — with KV compression (CacheGen) and non-prefix reuse (CacheBlend). Enable it when:

  • Branch revival latency matters. Without LMCache, evicted branches must be re-prefilled from tokens (compute-bound). With LMCache, evicted KV is demoted to CPU DRAM or NVMe first — revival reloads from cold store (bandwidth-bound, faster for conversations >512 tokens).
  • Cross-branch graft optimization. CacheBlend can reuse non-contiguous KV segments from cold-stored sibling branches, avoiding full re-prefill for graft operations.
  • Distributed branch migration. RDMA/NIXL transfer allows migrating cold-stored branch KV to a different GPU/node.

LMCache already integrates with SGLang — the cold-store tier connects directly to the eviction path. See Section 5b for the detailed design.

Section 5b

Cold-Storage Tier: LMCache / Mooncake for Branch Persistence

Agent chat branches are revisited minutes or hours after creation. Without a cold-storage tier, an evicted branch's KV must be re-prefilled from tokens on revival — expensive for long conversations. LMCache and Mooncake provide the missing tier: demote before discard.

The three-tier eviction cascade

Eviction is no longer a binary "cached in HBM or gone." It becomes a demotion chain:

Branch KV lifecycle:

  ┌─────────┐   evict    ┌─────────────┐   expire   ┌──────────┐
  │ GPU HBM │ ─────────→ │ Cold Store  │ ──────────→ │ Discarded│
  │ (hot)   │            │ (warm)      │             │ (replay) │
  └─────────┘            └─────────────┘             └──────────┘
       ↑     ← reload ←       │
       │                       │
  kvcached maps          LMCache stores
  physical pages         in CPU DRAM / NVMe / Redis / S3
  • Hot (GPU HBM): Active branch. KV in SGLang's KV pool, managed by the radix tree. Zero-latency attention access.
  • Warm (Cold Store): Idle branch, KV demoted to CPU DRAM or NVMe via LMCache. Branch metadata (token sequence, branch handle, tree position) remains in the Branch Manager. Revival = reload KV from cold store into fresh pool blocks. Latency: PCIe/NVMe bandwidth-bound, not compute-bound.
  • Discarded: Branch KV fully evicted from all tiers. Revival = full re-prefill from token history. Token history is always retained (tiny compared to KV).

Recompute vs. reload crossover

Demotion to cold store is only worthwhile when reloading from cold store is faster than re-prefilling. The crossover depends on prefix length and hardware:

Cold tierBandwidthCrossover (7B model)Crossover (70B model)
CPU DRAM (PCIe 5.0) ~64 GB/s ~512 tokens ~128 tokens
NVMe SSD (PCIe 4.0) ~7 GB/s ~4K tokens ~1K tokens
Redis (network) ~1-10 GB/s ~16K tokens ~4K tokens
S3 (remote) ~0.5 GB/s Rarely wins ~32K+ tokens

For agent chat sessions with typical conversation lengths of 2K–16K tokens, CPU DRAM and NVMe are both firmly in the "reload wins" zone. Redis is marginal. S3 is useful only as archival persistence for very long conversations. LMCache supports all four backends — the Branch Manager selects the tier based on branch age and expected revival probability.

KV compression for cold branches

LMCache's CacheGen compresses KV tensors before cold storage, reducing the storage footprint and reload bandwidth. Compression ratios of 3–5× are typical for KV data. This makes NVMe and Redis tiers more viable by effectively multiplying their bandwidth. The tradeoff is decompression latency on the GPU at reload time — but for cold branch revival (which is already a second-scale operation), this is negligible.

Non-prefix reuse via CacheBlend

LMCache's CacheBlend enables reusing KV from non-contiguous prefix matches — if two branches share scattered segments (not just a common prefix), CacheBlend can selectively reload the matching segments and recompute only the gaps. This is particularly relevant for the cross-branch graft use case ("redo steps 3–5 but keep step 6"), where the grafted branch shares non-contiguous segments with multiple source branches.

Integration architecture

class ColdStoreTier:
    def __init__(self, backend: str = "lmcache"):
        if backend == "lmcache":
            self.store = LMCacheClient(
                local_device="cpu",       # CPU DRAM as first-level cold store
                remote_url=None,          # optional Redis/S3 for deeper archival
                compression="cachegen",   # KV compression enabled
            )
        elif backend == "mooncake":
            self.store = MooncakeStoreClient(...)

    def demote(self, branch: BranchHandle, kv_blocks: list[int],
               allocator: TokenToKVPoolAllocator):
        """Evicted from GPU — write KV to cold store before freeing pool blocks."""
        kv_data = read_kv_from_gpu(kv_blocks)        # read before free
        self.store.put(
            key=branch.cold_store_key(),              # (branch_id, model_version, position_range)
            data=kv_data,
        )
        allocator.free(kv_blocks)                     # return blocks to SGLang's KV pool
        branch.cold_store_state = ColdStoreState.WARM

    def promote(self, branch: BranchHandle,
                allocator: TokenToKVPoolAllocator) -> list[int]:
        """Branch revived — reload KV from cold store into fresh pool blocks."""
        kv_data = self.store.get(branch.cold_store_key())
        if kv_data is None:
            branch.cold_store_state = ColdStoreState.DISCARDED
            return []                                 # must re-prefill from tokens
        new_blocks = allocator.alloc(len(kv_data))
        write_kv_to_gpu(new_blocks, kv_data)          # decompress + copy to HBM
        branch.cold_store_state = ColdStoreState.HOT
        return new_blocks

    def discard(self, branch: BranchHandle):
        """Permanently delete cold KV — branch can only be revived via re-prefill."""
        self.store.delete(branch.cold_store_key())
        branch.cold_store_state = ColdStoreState.DISCARDED

Cold-store-aware eviction policy

The eviction policy from Section 6.2 gains a new dimension: demotion cost. Before evicting a node, the Branch Manager checks whether the cold store has capacity and whether the KV is long enough to justify demotion (above the recompute-vs-reload crossover). Short branches skip cold storage and go straight to "discarded."

def evict_with_demotion(node, cold_store):
    if node.pinned:
        return  # never evict

    if cold_store and node.kv_length >= RELOAD_CROSSOVER_THRESHOLD:
        # Demote to cold store — worth the storage cost
        cold_store.demote(node.branch, node.kv_blocks, allocator)
    else:
        # No cold store, or too short to justify — free blocks and discard
        allocator.free(node.kv_blocks)
        node.branch.cold_store_state = ColdStoreState.DISCARDED

Model version invalidation

Cold-stored KV is model-version-bound: it was computed by specific model weights and is invalid after a model update. The cold store key includes model_version_hash. On model swap, all cold entries for the old version are either bulk-deleted or left to expire naturally via TTL. The Branch Manager does not attempt to reload stale KV — it falls back to re-prefill.

Detailed Design

6.1   Branch Manager: Session-Level API

The Branch Manager is a new module in sglang.srt.mem_cache. It provides a client-facing API for branch operations and translates them into radix tree + allocator operations.

Core data model

class BranchHandle:
    branch_id: str              # unique identifier
    branch_type: BranchType     # USER | SANDBOX | CHECKPOINT
    parent_id: str | None       # parent branch (None for root)
    fork_position: int          # token position where this branch diverges
    token_sequence: list[int]   # full token sequence for this branch
    pinned: bool                # if True, eviction cannot touch this branch's shared prefix
    model_version: str          # hash of model weights — KV valid only for this version
    created_at: float
    last_accessed: float

class BranchType(Enum):
    USER = "user"               # persistent, user-navigable
    SANDBOX = "sandbox"         # ephemeral, auto-deleted on commit/rollback
    CHECKPOINT = "checkpoint"   # savepoint within a sandbox exploration

6.2   Tree-Topology-Aware Eviction

Current SGLang eviction is leaf-first LRU. This implicitly protects shared prefixes (a parent can't be evicted until all children are gone) but doesn't weight nodes by structural importance. The extension:

Eviction priority = f(branch_type, descendant_count, recency, pin_state)

def eviction_priority(node):
    if node.pinned:
        return float('inf')  # never evict

    base = node.last_access_time

    # Structural weight: more descendants = harder to evict
    descendant_bonus = log2(1 + node.live_descendant_count) * DESCENDANT_WEIGHT

    # Branch type: sandbox nodes evict aggressively after commit/rollback
    type_penalty = {
        BranchType.USER: 0,
        BranchType.CHECKPOINT: -CHECKPOINT_PENALTY,
        BranchType.SANDBOX: -SANDBOX_PENALTY if node.committed_or_rolled_back else 0,
    }[node.branch_type]

    return base + descendant_bonus + type_penalty

Key properties:

  • Shared interior nodes with many descendants are protected by descendant_bonus, not just by leaf-first ordering.
  • Committed/rolled-back sandbox nodes are evicted aggressively — their KV is dead weight.
  • Pinned nodes are unevictable; the user explicitly declared them important.
  • Leaf-first is preserved as a tiebreaker within the same priority band.

Integration with allocator and cold store

Eviction triggers an optional demotion cascade before freeing blocks:

  1. Radix tree eviction: SGLang's eviction selects a node via eviction_priority().
  2. Cold-store demotion (if LMCache enabled): If the node's KV length exceeds the reload crossover threshold (Section 5b), the Branch Manager writes KV to LMCache before freeing blocks. The branch transitions from HOT to WARM.
  3. Block free: Block indices return to the pool via allocator.free(). (If kvcached is enabled, this triggers cuMemUnmap on physical pages. With SGLang's stock allocator, blocks simply return to the free list.)

On branch revival, the Branch Manager checks cold store first (if available). On hit: reload KV from CPU DRAM/NVMe (bandwidth-bound, fast). On miss or no cold store: full re-prefill from token history (compute-bound, slow). The radix tree's match_prefix() handles both paths — a cold-store reload inserts the KV back into the tree as if it were a fresh prefill.

6.3   KV Validity Across Mutations

A radix tree keys on (token_id, position). This is insufficient when the same token sequence yields different KV under different conditions.

Extended cache key

CacheKey = (token_ids: tuple[int], model_version_hash: str, segment_id: str)

# model_version_hash: SHA256 of model checkpoint — KV from model A
#   is invalid under model B even if tokens match.
# segment_id: distinguishes volatile segments (system prompt, RAG context)
#   from stable segments (conversation history). A system prompt change
#   invalidates only the system-prompt segment's KV, not the conversation.

Segment-aware prefix matching

The token sequence is divided into segments: [system_prompt | conversation | tool_results | ...]. Each segment has a segment_id derived from its content hash. When matching prefixes, the radix tree matches segment-by-segment, allowing a system prompt change to invalidate only the first segment while preserving the conversation prefix match.

This prevents two failure modes:

  • False positive: tokens match but KV is from a different model. Caught by model_version_hash mismatch → cache miss → re-prefill.
  • False negative: system prompt changed, so the entire token sequence mismatches even though the conversation is identical. Segment-aware matching preserves the conversation hit.

Cross-branch graft

"Redo steps 3–5 but keep step 6" requires composing content from two branches. The merged token sequence is novel — neither branch's KV covers it. RoPE embeds absolute position into K, so KV blocks can't be spliced across position boundaries. The Branch Manager handles this as:

  1. Create new branch at the divergence point (step 2).
  2. Generate new content for steps 3–5.
  3. Append step 6's tokens (not KV) from the old branch.
  4. Re-prefill from the graft point. The shared prefix (steps 0–2) is a radix tree cache hit; only steps 3–6 are recomputed.

6.4   Tool-Sandbox Two-Phase Commit

A sandbox branch touches two state spaces: KV cache (inside SGLang) and world state (files, APIs, databases). COW on KV alone gives "undo the conversation"; COW on both gives "undo the action."

Protocol

# Fork
kv_branch = branch_manager.fork_sandbox(parent, tool_call)
env_snapshot = environment_plugin.snapshot()  # filesystem, DB, etc.

# Execute
result = tool_executor.run(tool_call, sandbox_env=env_snapshot)

# Decide
if user_approves(result):
    branch_manager.commit_sandbox(kv_branch)   # KV: sandbox becomes main
    environment_plugin.promote(env_snapshot)     # World: make side-effects real
else:
    branch_manager.rollback_sandbox(kv_branch)  # KV: discard sandbox subtree
    environment_plugin.revert(env_snapshot)      # World: undo side-effects

Environment plugin interface

class EnvironmentPlugin(Protocol):
    def snapshot(self) -> SnapshotHandle: ...
    def promote(self, handle: SnapshotHandle) -> None: ...

Merge semantics

Three cases, escalating in complexity:

  • Linear commit: Sandbox is the only active branch. Commit = pointer swap (sandbox child becomes main tip). KV is already correct.
  • Commit with diverged main: Main advanced while sandbox ran. Requires rebase: replay sandbox's tool result after main's new content. KV from the insertion point must be recomputed. The shared prefix (up to the fork point) is a cache hit.
  • Multi-branch merge: N sandbox results combined into one continuation. The merged token sequence is novel — re-prefill from the fork point with combined content. Shared prefix KV is reused.
Section 7

N-Branch Active Workload Optimizations

When multiple branches are simultaneously active in the same batch (best-of-N, speculative tool execution, parallel strategies), the bottleneck shifts from cache management to compute efficiency.

Shared-prefix attention kernel

Today, even though N sibling branches share the same prefix KV in storage (via radix tree), each branch reads the prefix K,V tensors independently from HBM during attention. For prefix length L with N branches, that's (N−1)×L×num_heads×head_dim×2 bytes of redundant HBM bandwidth per layer per decode step.

Key insight: The radix tree knows which sequences share which prefix nodes. This topology should drive a fused attention kernel that loads shared-prefix K,V tiles once into SRAM and processes all N branches' queries against them. Per-branch state (running softmax accumulators) is O(head_dim) per branch — ~12KB for N=16, well within shared memory.

Sibling-affine batch scheduling

The shared-prefix kernel only fires when siblings land in the same batch. A branch-aware scheduler should prefer to co-schedule siblings (same parent in the radix tree) and keep sibling groups together across iterations.

Partial-generation scoring + pruning

For speculative tool execution: score partial completions every K tokens, kill low-scoring branches early. The radix tree makes freeing a branch trivial (dec_ref → leaf eviction → blocks returned to pool).

Section 9

Open Questions

  • Upstream strategy: Contribute branching features to SGLang upstream, or maintain a fork? Upstream is cleaner long-term but requires community alignment. The modifications touch core paths (RadixCache, scheduler, attention backend) — upstream acceptance depends on whether the SGLang team sees branching as a first-class use case.
  • kvcached autopatch non-regression: Branching modifies RadixCache and adds BranchManager above the allocator. kvcached patches the allocator below. These should be non-overlapping, but need continuous testing to ensure kvcached's autopatch doesn't break on branching-modified SGLang. Integration test matrix: {stock allocator, kvcached} × {no cold store, LMCache}.
  • Branch garbage collection policy: How long should an unpinned, unvisited branch survive before eviction? Time-based decay, or count-based (keep last N branches)? Should cold-store TTL differ from GPU eviction TTL?
  • LMCache vs. HiRadixCache for demotion: SGLang's HiRadixCache already supports CPU-tier demotion natively. LMCache offers more backends (NVMe, Redis, S3), compression, and non-prefix reuse. Should we use HiRadixCache for local CPU demotion and LMCache only for deeper tiers? Or bypass HiRadixCache entirely and use LMCache uniformly?
  • Cold-store capacity planning: How much CPU DRAM / NVMe should be provisioned for cold branches? For a system serving 1000 concurrent agent sessions with avg. 3 branches each, cold-store capacity = ~3000 × avg_branch_KV_size. With CacheGen compression (3–5×), this is tractable for CPU DRAM on typical servers.
  • CacheBlend for cross-branch graft: LMCache's CacheBlend can reuse non-contiguous KV segments. For the graft use case ("redo steps 3–5, keep step 6"), CacheBlend could reload step 6's KV from a cold-stored sibling branch. Needs integration work — CacheBlend's segment matching must be aware of the branch tree structure.
  • Sandbox environment plugin standardization: What's the minimal interface that covers filesystem, database, and container sandboxing without being so abstract it's useless?
  • RoPE-free architectures: If the model uses ALiBi or NoPE instead of RoPE, KV blocks might be position-independent, enabling true cross-branch KV splicing. Worth investigating for graft operations.
