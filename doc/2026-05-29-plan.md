# Caden Implementation Plan — Stage-Aware Scheduling for Dense AI-Agent Sandboxes

Status: active plan, revised 2026-06-01.

This supersedes the old tool-call/intent Caden plan and the CPU-only `sched_ext`
framing. The core claim is now broader: AI-agent sandboxes move through distinct
execution stages, and the host can safely overcommit CPU and memory by treating
LLM-waiting sandboxes as cold/resumable tenants while keeping local execution
bursts hot.

## Goal

Build and evaluate Caden: a stage-aware host scheduler for densely packed
AI-agent sandboxes. Caden tracks each sandbox as it moves through:

```text
LLM_WAIT -> RESPONSE_WAKE -> TOOL_BURST -> RESULT_PACK -> LLM_WAIT
```

and assigns CPU priority, memory residency, and admission decisions based on the
current stage, criticality class, and expected next local burst.

The headline metric is **agents per host at an interactive turn-latency SLO**.
The key wedge is not only CPU fairness during bursts; it is dynamic overcommit:
waiting sandboxes should not keep full hot CPU/memory residency while their next
action is blocked on a remote LLM.

## Core Thesis

Static container isolation assumes each sandbox is live all the time. AI agents
are not. Most wall-clock time is spent in off-host LLM stages, while local host
work arrives as short CPU/memory/IO bursts. Caden exploits this stage imbalance:

- `LLM_WAIT`: freeze or demote the sandbox, make memory reclaimable, and admit
  more sandboxes.
- `RESPONSE_WAKE`: thaw/prewarm the sandbox before or as the response arrives.
- `TOOL_BURST`: protect interactive local execution with bounded CPU/memory
  priority.
- `RESULT_PACK`: finish short result collection quickly, then return to cold
  wait state.

The pipeline-parallel analogy: keep the host-side execution stage full without
allocating hot host resources to every off-host LLM-wait stage.

## SWE-Rebench Trace Evidence

The first SWE-rebench/SWE-bench-style Claude Code trace pass supports the
stage-pattern premise. The reproducible analysis is in
`analysis/analyze_local_trace_stages.py`; the generated report is
`eval/local-trace-stage-report.md`.

On 2026-06-01, scanning `agentcgroup/experiments` found 190 trace files and 157
comparable timestamped traces with tool-call timing. Across those traces:

- classified LLM wait accounts for 66.3% of observed LLM-wait plus local-tool
  stage time;
- local tool execution accounts for 33.7%;
- 134/157 traces, or 85.4%, show the recurring
  `tool -> tool_result -> LLM_WAIT -> assistant` pattern;
- median per-trace LLM fraction is 69.3%, and p90 is 91.6%;
- median alternation coverage is 100.0%: almost every local tool call is
  followed by an observable LLM wait.

This is evidence for the scheduling opportunity, not evidence that Caden wins.
Experiment 0 remains the gate: Caden must beat static cgroup/admission baselines
at fixed density and SLO before moving to headline density claims.

Scope caveat: this evidence is still SWE-rebench-derived coding-agent workload
evidence. It should not be presented as a general sample of all local AI-agent
activity until Caden also collects non-SWE interactive traces.

## Acceptance Criteria

Each criterion has positive and negative tests.

- **AC-1 — Stage-aware multi-sandbox harness.** A driver launches N container
  sandboxes on one Linux host, one cgroup v2 per sandbox, and replays
  configurable agent loops with explicit stage transitions.
  - PASS: a run with N=32 records per sandbox and per turn:
    `sandbox_id`, `class`, `stage`, `stage_enter_ts`, `stage_exit_ts`,
    `submit_ts`, `llm_wait_ms`, `burst_start_ts`, `burst_end_ts`,
    `cpu_time_ms`, `memory_current_bytes`, `major_faults`, and host CPU/RAM
    utilization.
  - PASS: both synthetic loops and trace-derived loops from
    `agentcgroup/experiments` can drive the harness.
  - FAIL: a run where multiple sandboxes share one cgroup is rejected.
  - FAIL: a `TOOL_BURST` implemented as only `sleep` is rejected; bursts must
    consume measurable CPU, memory, or IO.

- **AC-2 — Stage declaration and detection.** Caden classifies each sandbox into
  `LLM_WAIT`, `RESPONSE_WAKE`, `TOOL_BURST`, `RESULT_PACK`, or `UNKNOWN`.
  - PASS: cooperative mode marks LLM request send, LLM response receive, local
    tool start, and local result-pack end through the Caden shim with >=99%
    accuracy against harness labels.
  - PASS: transparent mode infers `TOOL_BURST` and idle/cold state from runnable
    transitions and cgroup activity with >=90% accuracy on labeled runs.
  - FAIL: an `UNKNOWN` sandbox is never promoted as interactive-hot without a
    logged reason.

- **AC-3 — Criticality declaration.** Each sandbox is `interactive` or
  `background`, visible to both the userspace controller and the scheduler.
  - PASS: class is stored in a BPF map keyed by cgroup id and/or in a controller
    state table that is reflected into scheduler policy.
  - FAIL: an undeclared sandbox defaults to `background` and is logged.

- **AC-4 — Memory residency control.** Caden demotes LLM-waiting sandboxes and
  restores them before local work violates the SLO.
  - PASS: in `LLM_WAIT`, Caden can freeze the sandbox and trigger cgroup v2
    reclaim (`memory.reclaim`) or equivalent cold-memory demotion; reclaimed
    bytes and wake latency are recorded.
  - PASS: on `RESPONSE_WAKE`, Caden thaws/prewarms the sandbox and records thaw
    latency, major faults, and time-to-first-dispatch.
  - FAIL: a sandbox cannot remain frozen after a response arrives unless it is
    explicitly rejected by admission control.
  - FAIL: reclaim that causes OOM or unrecoverable sandbox failure aborts the run.

- **AC-5 — Local execution CPU policy.** A `sched_ext` scheduler extending
  AgentCgroup's `scx_flatcg` assigns dynamic CPU priority from
  `f(stage, class, burst_age)`.
  - PASS: `RESPONSE_WAKE` and newly active interactive `TOOL_BURST` sandboxes
    receive bounded priority boost; long-running bursts decay; background
    sandboxes retain non-zero forward progress.
  - PASS: loads on stock Ubuntu 24.04 with Linux 6.12+ through the userspace
    loader and survives a >=30 minute watchdog-clean run.
  - FAIL: any watchdog unload caused by stalled tasks.
  - FAIL: any background sandbox receives zero CPU over a 10 s window while CPU
    capacity is available.

- **AC-6 — Admission control and wake-storm headroom.** Caden admits new
  sandboxes only while preserving enough headroom for likely returning LLM waits.
  - PASS: the controller maintains a configurable hot-capacity budget derived
    from active sandboxes plus expected near-term responses.
  - PASS: under a synthetic wake storm, Caden rejects or delays new admissions
    rather than thawing all waiting sandboxes into OOM or SLO collapse.
  - FAIL: a run that admits more cold sandboxes while the predicted hot budget is
    already exhausted.

- **AC-7 — Observability and metric closure.** Run records suffice to compute
  all headline metrics without external joins.
  - PASS: every run includes per-turn records, per-stage records, residency
    events, scheduler decision logs, baseline (`B0`/`B1`/`B2`/`B3`), `run_id`,
    and a host manifest with cores, RAM, kernel, swap/zswap state, container
    runtime, density, and pre-registration commit.
  - PASS: a single analysis command computes per-class p50/p95/p99 turn latency,
    thaw latency, local burst latency, memory reclaimed per cold sandbox, and
    max agents/host at SLO.
  - FAIL: missing required fields abort analysis.

- **AC-8 — Premise gate, Experiment 0.** At fixed density and pre-registered
  SLO, stage-aware Caden beats static cgroup CPU/memory policy.
  - PASS: Caden sustains higher agents/host at the SLO than static
    `cpu.weight`/`cpu.max` plus static memory limits, OR materially lowers
    interactive p99 at equal density, with n >= 3 and pre-registered tests.
  - FAIL: if static policy matches Caden within the registered margin, the
    density premise is unsupported and the project pivots.

- **AC-9 — Density at SLO, headline E1.**
  - PASS: across `B0` default Linux, `B1` static cgroups, `B2` CPU-only Caden,
    and `B3` stage-aware Caden, `B3` sustains the highest agents/host at the
    interactive turn-latency SLO with confidence intervals over n >= 3.
  - FAIL: `B3` is not strictly above `B0`.

- **AC-10 — Mixed-criticality and wake-storm protection, E2.**
  - PASS: with fixed interactive population and increasing background load,
    Caden keeps interactive p99 below SLO past the density where B0/B1 breach it.
  - PASS: under batched LLM responses, Caden's admission/headroom policy avoids
    memory collapse and bounds thaw-induced tail latency.
  - FAIL: interactive p99 under B3 degrades to within 10% of B0 at target
    density.

- **AC-11 — Overhead and safety, E5.**
  - PASS: Caden adds <=3% host CPU overhead at idle and <=5% under load vs CFS;
    per-dispatch decision cost, controller polling cost, reclaim cost, and thaw
    cost are reported.
  - FAIL: >10% overhead in either regime or any unrecovered sandbox failure.

- **AC-12 — Novelty and pre-registration.**
  - PASS: `doc/eval/novelty-recheck.md` surveys 2025-26 eBPF, `sched_ext`,
    container overcommit, checkpoint/restore, serverless cold-start, and
    agent-scheduling work. `doc/eval/preregistration.md` fixes SLOs, density
    definitions, effects, n, tests, baselines, and exclusion rules before E0/E1/E2.
  - FAIL: a headline run whose manifest references a pre-registration commit
    that is not an ancestor of the run commit.

## Baselines

- **B0 — Default Linux:** CFS, no Caden residency policy, default cgroup behavior.
- **B1 — Static cgroups:** fixed `cpu.weight`/`cpu.max`, fixed memory limits or
  `memory.high`/`memory.low` reservations.
- **B2 — CPU-only Caden:** stage/class-aware `sched_ext` boost for local bursts,
  no wait-state memory demotion or admission overcommit.
- **B3 — Stage-aware Caden:** CPU-only Caden plus stage-aware freeze, reclaim,
  prewarm, and admission/headroom policy.

## Path Boundaries

**Upper bound:** full stage-aware Caden with cooperative and transparent stage
detection, freeze/reclaim/prewarm residency control, `sched_ext` CPU policy,
admission control, wake-storm experiments, and optional zswap/CRIU comparisons.

**Lower bound:** cooperative stage detection, cgroup freezer, cgroup v2 memory
reclaim, static prewarm policy, CPU-only `sched_ext` boost, and E0/E1/E2/E5 on a
single stock-kernel host. No CRIU, no custom kernel, no `cache_ext`.

**Allowed:** C/Rust/BPF for scheduler and controller; Python for harness/eval;
podman or runc for sandboxes; stock Ubuntu 24.04 with Linux 6.12+; zswap/swap
only when explicitly captured in the host manifest.

**Not allowed for the core:** custom out-of-tree kernels, sleep-only burst
stand-ins, treating undeclared sandboxes as interactive, or hiding wake failures
as excluded data.

## Milestones

- **M0 — Gates.** Novelty re-check; harness MVP with explicit stages; B0/B1
  baselines; minimal B2 CPU-only Caden; minimal B3 freeze/reclaim policy; run E0.
  Proceed only if B3 or B2+B3 combination beats static cgroups.
- **M1 — Harness and observability.** Full multi-sandbox stage harness,
  synthetic and trace-derived generators, manifest schema, metric query, and
  validator.
- **M2 — Residency controller.** Cooperative stage shim; freezer integration;
  `memory.reclaim`; prewarm/thaw path; headroom/admission policy.
- **M3 — CPU scheduler.** Extend `scx_flatcg` into stage/class/burst-age
  scheduler; validate watchdog and forward progress.
- **M4 — Transparent detection.** Infer stages from runnable transitions,
  cgroup activity, and process events; compare against cooperative mode.
- **M5 — Experiments.** Pre-registration, then E1 density-at-SLO, E2
  mixed-criticality and wake storms, E3 scale, E5 overhead.
- **M6 — Paper.** Position as stage-aware sandbox scheduling for dense AI-agent
  hosts; CPU scheduling and memory residency are the two enforcement levers.

Dependencies: M0 gates the project. M1 enables M2/M3. M2 and M3 enable M5.
`cache_ext` page-cache QoS and CRIU are post-M5 optional comparisons.

## Risks

- **Premise risk:** static cgroups plus simple admission may be close to Caden.
  E0 runs first.
- **Wake-storm risk:** aggressive cold demotion can create synchronized major
  faults. AC-6 makes headroom policy mandatory.
- **Memory reclaim risk:** `memory.reclaim` may not reclaim enough useful memory
  without swap/zswap or may harm wake latency. Measure reclaimed bytes and thaw
  p99 as first-class outputs.
- **Stage-signal risk:** transparent inference may be noisy. Cooperative mode is
  the lower-bound path.
- **Scheduler risk:** `sched_ext` may consume time. B3 residency control must
  still be measurable with stock cgroup mechanisms, while B2/B3 CPU enforcement
  uses `sched_ext` when available.
- **Novelty risk:** this now overlaps serverless cold-start, container
  overcommit, and checkpoint/restore literature. t1 must position the agent
  stage structure and turn-latency metric clearly.
